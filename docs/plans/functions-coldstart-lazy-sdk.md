# Plan: Fix gen2 deploy cold-start failures via lazy SDK loading

## Problem / root cause

Firebase 2nd-gen deploys to `live` intermittently fail with:

> Could not create or update Cloud Run service `<fn>`, Container Healthcheck
> failed ... the user-provided container failed to start and listen on the port
> defined provided by the `PORT=8080` environment variable within the allocated
> timeout.

A different small subset of functions fails on each run (e.g. `getGithubConnection`,
`updateGithubConnectionSettings`, `disconnectGithub`, `getGithubOAuthConfig`), which
is why it reads as "flakiness."

Root cause: all functions live in a single codebase (`functions/`, `main: lib/index.js`).
In gen2 every function is its own Cloud Run service, but they all boot from the same
bundle and must `require()` the entire `index.js` module graph **before the container
can listen on `PORT=8080`**. `index.ts` eagerly imports and constructs heavy SDKs at
module scope:

- `import { google } from 'googleapis'` + `google.tasks('v1')` / `google.people('v1')` (module scope)
- `import { VertexAI } from '@google-cloud/vertexai'` + `new VertexAI(...)` / `getGenerativeModel(...)` (module scope)
- `import * as nodemailer` and `import { marked, Renderer }`

`googleapis` (umbrella) + `vertexai` are multi-second to load. PR #188 raised
memory/CPU on the heavy functions so they boot in time; the lightweight callables
(GitHub connection management, etc.) stayed at the 256MiB floor (lowest CPU) yet still
pay the full heavy-import tax, so they are the ones that cross the startup-healthcheck
deadline. PR #191 added deploy retries — this masks the failed deploys but does
nothing for runtime cold-start latency and leaves deploys fragile.

## Fix

Load the heavy SDKs lazily (on first use inside the handlers that need them) instead
of at module scope. Then every container boots with only `firebase-functions` +
`firebase-admin`, comfortably inside the healthcheck window. The Tasks / People /
OAuth / Vertex / email functions load their SDK on first invocation, after the
container is already serving.

This is the proper fix that the #191 retry only papered over. The previously
discussed us-east1 region migration is orthogonal and would NOT fix this (a region
migration re-creates every function, which is *more* exposed to cold-start timeouts).

## Scope / files affected

- `functions/src/index.ts` — convert eager imports + module-scope clients to lazy
  memoized getters; update call sites.
- `functions/lib/index.js` (+ `.map`) — regenerated by `tsc` (git-tracked; the deploy
  uses the committed output because there is no `predeploy` hook and the deploy
  workflow runs `npm ci` without a build step).
- `docs/plans/functions-coldstart-lazy-sdk.md` — this plan.

No change to `functions/src/github/*` (those never used the heavy SDKs), no Firestore
rules, no Angular, no workflow changes.

## Implementation steps

1. Replace runtime imports with `import type` where only types are needed
   (`tasks_v1`, `people_v1`, `GenerativeModel`, `Transporter`); drop the `marked`
   runtime import.
2. Add lazy memoized getters near the top of `index.ts`:
   `getGoogle()`, `getTasksApi()`, `getPeopleApi()`, `getNodemailer()`, `getGeminiModel()`.
   Each `require()`s its module on first call (Node caches the module; clients are
   memoized in module-scope vars).
3. Move `new Renderer()` / `marked.parse()` behind a `require('marked')` inside
   `markdownToEmailHtml`.
4. Update call sites: `google.auth.OAuth2` → `getGoogle().auth.OAuth2`;
   `tasksApi` → `getTasksApi()`; `peopleApi` → `getPeopleApi()`;
   `geminiModel` → `getGeminiModel()`; `nodemailer.createTransport` →
   `getNodemailer().createTransport`; `nodemailer.Transporter` type → `Transporter`.
5. `cd functions && npm run build` to regenerate `lib/`, then run `npm test`.
6. Commit `src/` + regenerated `lib/index.js`/`.map` together.

## Test plan

- `cd functions && npm run build` — TypeScript compiles under `strict` + `noUnusedLocals`.
- `cd functions && npm test` — existing `node --test` suite passes.
- Static grep: no remaining module-scope `google.`/`VertexAI`/`nodemailer.`/`marked`
  references outside the lazy getters.
- PR CI (`pr-validation.yml`) re-runs the functions build.
- Post-merge: watch the `live` deploy — functions should deploy without healthcheck
  retries.

## Rollback considerations

- Pure refactor; behavior is unchanged (same SDKs, same config, same call results) —
  only *when* the modules load changes. First invocation of a Tasks/People/Vertex/email
  function pays a one-time module-load cost (previously paid at container start).
- Revert is a single-commit `git revert` (src + lib together); no data migration, no
  rules change, no infra state to unwind.
- If a lazy `require()` ever failed at runtime it would surface as an error on first
  invocation of that specific function rather than a deploy failure — strictly easier
  to diagnose than the current opaque healthcheck timeout.
